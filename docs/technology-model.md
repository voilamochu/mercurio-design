# Technology Renderer Model

## Why this intermediate model exists

`source/data/technologies.json` is the canonical, engine-independent source of truth
for technology card data. It is authored and maintained by designers and is the single
place where gameplay facts (name, level, type, copies, description, project details) live.

Renderers should never consume the canonical file directly. Renderers need a different
shape of data: stable, sequential, zero-ambiguity rendering metadata that is safe to read
without re-implementing derivation logic in every renderer (SVG, HTML preview, print
export, BGA export, etc.).

`compiler/build-tech-model.js` converts the canonical source into
`generated/models/technologies.json` — the **renderer model**. This is a deliberate
separation: the canonical file is edited; the generated model is produced. The canonical
file can change shape without breaking renderers, as long as the compiler absorbs the
difference.

## Canonical data vs. renderer model

| Concern            | Canonical (`source/data/technologies.json`)        | Renderer (`generated/models/technologies.json`)      |
|--------------------|----------------------------------------------------|------------------------------------------------------|
| Ownership          | Authored by designers                              | Generated by compiler                                |
| Source of edit     | Yes                                                | No (do not hand-edit)                                |
| Gameplay facts     | `id`, `name`, `level`, `type`, `copies`, `description`, project fields | Same facts, copied verbatim (no mechanics invented) |
| Rendering metadata | Absent                                             | Derived/populated (`assetId`, `romanLevel`, `frameStyle`, ...) |
| Stability          | May change shape                                   | Stable contract for renderers                        |

The compiler copies gameplay fields exactly and **only derives rendering metadata**. It
never invents gameplay mechanics.

## Derived fields

Each technology record in the renderer model gains the following fields:

- **sequentialIndex** — 0-based position in the array (stable render order).
- **assetId** — Stable identifier `tech_001`, `tech_002`, ... (3-digit zero padded, maps to future artwork slots).
- **artworkDomain** — Placeholder `"unassigned"`; replaced later by the technology artwork mapping.
- **artworkOverlay** — Placeholder `"unassigned"`; replaced later by the technology artwork mapping.
- **artworkVariant** — Default `"placeholder"` until a real variant is assigned.
- **frameStyle** — Derived from `type`. One of `Project`, `Passive`, `Active`, `Endgame` (drives frame geometry/decoration choice).
- **frameColor** — Color keyed to `frameStyle` (`Project` blue, `Passive` green, `Active` amber, `Endgame` purple); drives frame stroke/fill in renderers.
- **romanLevel** — Numeric `level` → roman numeral (`1`→`I`, `2`→`II`, `3`→`III`); shown directly in the card frame.
- **displayLevel** — Human-friendly `"Level N"` string for rendering.
- **displayType** — Human-friendly version of `type` for rendering.
- **flavorText** — Empty placeholder `""`; populated later (no gameplay meaning).
- **rendererVersion** — `"v1"`; lets renderers detect model contract version.

## Why renderers should ONLY consume `generated/models/technologies.json`

- It is the stable contract. Gameplay data and rendering metadata are already merged, so
  each renderer avoids duplicating derivation logic (roman numerals, asset ids, frame styles).
- It guarantees validation has already passed (exactly 40 technologies, unique ids and
  assetIds, sequential indices, correct roman numerals, valid frame styles).
- Hand-editing the canonical file cannot silently break renderers; the compiler is the only
  transform, and it fails loudly (aborts on validation failure) before any output is written.
- Future artwork mapping and flavor text will be injected by the compiler, keeping renderers
  untouched.

## Pipeline

```
source/data/technologies.json   (canonical, hand-authored)
        │
        │  npm run build:tech-model
        ▼
compiler/build-tech-model.js    (derives rendering metadata, validates)
        │
        ▼
generated/models/technologies.json   (renderer model — consume this only)
```
